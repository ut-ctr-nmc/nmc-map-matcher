# Modules (Directory Structure)

The NMC Map Matcher exists as a directory `nmc_mm_lib` representing a library. The "entry point" for that library is `graph.py` that offers classes and method for building up a base map, creating trackpoints, and running the map matching operation. (The workflow for these is best viewed in the `gtfs_small_sample.py` and `avl_osm_sample.py` sample codes). Meanwhile, to help the sample codes, supporting functions exist in the `support` directory, including a GTFS reader and a code that coordinates the retrieval of OpenStreetMap roadway networks using queries to the Overpass API.

`support/osm_overpass.py` optionally caches what it fetches to a JSON file (`osm_cache.json` in the case of `avl_osm_sample.py`), so that repeated runs do not re-query Overpass. Delete that file to force a fresh query; it is also discarded automatically if the bounding box, endpoint, or roadway-type filter it was built from no longer matches. Nodes and ways are keyed and emitted in OSM ID order, both into the cache file and into the map, so that a given query yields the same cache file and the same match results every time regardless of the order the API returned things in. That ordering matters more than it may appear: it decides ties among equally-close candidate links during matching, and unstable ordering used to make consecutive runs of identical code disagree. See [Performance](performance.md) for the details.

The earlier versions of the NMC Map Matcher had a multi-stage approach to map matching that worked well for gradually refining an underlying road network containing errors. (The most common errors were links that were not properly connected to intersection nodes). The gist of the workflow in Version 2.0 is to 1) run a first map matching operation with conservative parameters that produce gaps or discontinuities when the underlying map has errors. Then 2a) refine the underlying map and run again, or 2b) loosen the map matching parameters to allow for more "liberal" routing. In either case, Version 1.0 "problem reporting module" is now currently replaced with functionality in `nmc_mm_lib.reporter` for outputting map matching results.

Improvements over the Perrine et al. 2015 paper made in the last decade includes dramatic accelerations in geographic distance calculations, curved geometry, more flexibility in metadata and cost calculations, simplified demos and use cases, concrete examples checked into the repo, and generalization of the map matching problem to any type of geographic data.
